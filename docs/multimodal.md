# 多模态检索：把图片接进 RAG

## 1. 为什么做

图谱里两类实体带图：中药 2,876 张（502 味，平均 5.7 张）、化学成分结构式 13,728 张。
一开始只做「显示」——证据卡片配张图。但药材识别是个真实需求：
用户手里有一张照片，想知道这是什么药、能干什么。

这正好接上 RAG：**图片检索产出候选实体，候选实体再进图谱问答**，
形成「看图 → 定位实体 → 问答」的链路。

## 2. 为什么是 Chinese-CLIP

官方 CLIP 的文本塔基本只认英文，用户问「红色的果实」「干燥的绿色草质茎叶」时，
文本向量和图像向量根本对不上，检索等于随机。

Chinese-CLIP（`OFA-Sys/chinese-clip-vit-base-patch16`，189M 参数）用中文图文对训练，
才能让中文描述落到图像空间里。CPU 上加载 0.5 秒（缓存后），编码 7 张/秒。

## 3. 索引设计

三个和「一张封面代表一味药」不同的决策：

**① 每味药索引多张照片，检索时按药聚合取最高分。**
一味药的照片可能横跨原植物、饮片、粉末，角度光照都不同。只用封面代表，
换个拍摄条件就召不回来——实测只索引封面时，图搜图的 top-1 明显更差。

**② 索引里放的是 200px 缩略图的向量，不是 1.13GB 原图。**
CLIP 反正会把图缩到 224×224，用缩略图编码结果几乎一样，但读盘快几十倍，
整个索引只有 5.9MB（2,875 × 512 × 4 字节）。

**③ 图像检索和文本检索共用一套图像向量，差别只在查询走哪个塔。**
查询是图片就过图像塔，是文字就过文本塔，最后都在图像空间里比。
这才是跨模态；如果给每味药再建个「名字向量」去比文本，那只是文本匹配，换个说法就废了。

## 4. 关键发现：纯 CLIP 的文本塔对「药名」不敏感

第一版做完，以文搜图的实测很差：

| 查询 | 结果 |
| --- | --- |
| 人参 | 当归、高良姜、玄参、生姜、党参（**人参不在前五**） |
| 红色的果实 | 相思子、北五味子、山茱萸、白毛藤、南五味子（很好） |

**自由的外观描述效果好，但药名查询很差。** 原因是 Chinese-CLIP 在描述性 caption
上训练，「人参」这种词更接近「命名」而不是「视觉描述」，文本塔没学过把单实体名
映射到对应图像。

### 解决办法：给文本查询加一个实体级先验

为每味药预计算 `「药名，功效」` 的文本向量（502 条，13.8 秒），查询时与图像分数加权：

```
score = α · cos(查询, 药名+功效) + (1-α) · max_i cos(查询, 图_i)
```

α=0 退化为纯跨模态，α 越大越偏向实体名匹配。扫描 α：

| α | Top-1 | Top-3 | Top-5 | MRR |
| --- | --- | --- | --- | --- |
| 0.0（纯跨模态） | 20.0% | 33.3% | 40.0% | 0.277 |
| 0.3 | 62.7% | 77.3% | 82.0% | 0.709 |
| **0.5（采用）** | **69.3%** | **80.7%** | **86.0%** | **0.755** |
| 0.7 | 71.3% | 78.7% | 83.3% | 0.757 |
| 1.0（纯文本） | 69.3% | 76.0% | 78.7% | 0.729 |

**这张表说明了两件事**：
- 纯跨模态只有 40%，纯文本 78.7% —— 单靠任何一边都不够；
- 融合到 0.5 是 86.0%，比纯文本还高 7.3pp，**说明图像项提供的是额外信息，不是噪声**。
  如果图像没用，α=1 就该最好，事实并非如此。

（150 条药名查询，来源：每味药一条）

## 5. 图搜图的评测：leave-one-out

没有独立标注集，但每味药有多张照片，天然构成「同一实体的不同视角」。
所以拿某张照片去检索，**把它自己从候选里排除**，看能不能召回同一味药的其他照片。
索引里不包含查询图，不存在泄漏。

| 指标 | 数值 |
| --- | --- |
| 查询数 | 400（共 2,373 张可用） |
| Top-1 | 50.7% |
| Top-3 | 65.0% |
| **Top-5** | **70.8%** |
| MRR | 0.586 |

502 类的细粒度视觉检索，用通用域 CLIP 做到 top-5 70% 属于「可用的候选召回」，
但绝不能当鉴定结论——所以接口返回里带 `disclaimer`，前端也明确写「非鉴定结论」。

## 6. 怎么接进 RAG

```
上传照片 → /api/vision/search-image → 候选药（带相似度）
        → 点「追问这味药」→ 自动提问「X 含有哪些化学成分？」
        → 走原有 GraphRAG 链路（Text2Cypher / 混合检索 / 证据引用）
```

图片检索只负责「定位实体」，事实性回答仍然由图谱提供——
这样多模态输出也能被证据追溯，不会出现「模型看图编药效」。

## 7. 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/vision/search-image` | 上传图片（≤8MB）→ 候选中药 |
| GET | `/api/vision/search-text` | 中文描述/药名 → 候选中药，`alpha` 可覆盖默认融合权重 |
| GET | `/api/vision/stats` | 索引状态（图片数/药味数/是否含文本先验） |

安全上做了三件事：限制 8MB、用 PIL 真正解析一遍（拒绝伪装成图片的任意字节）、
解析失败不把异常原文抛给前端。

## 8. 已知局限

1. **不能当鉴定用**：相似度最高的不一定是正确答案，同属不同种的药材外观可能几乎一样；
2. **训练域不匹配**：Chinese-CLIP 是通用域模型，药材饮片属于长尾；
   换领域微调的 CLIP 或专门的细粒度模型能明显提升；
3. **文本先验 α=0.5 是在 150 条药名查询上调的**，样本不大，真实分布下可能要重调；
4. **单机内存**：CLIP + bge 两个模型同时常驻约 800MB，
   低配机器上应该用 ONNX 量化或改成按需加载。
