# 消融实验

只报「通过率 100%」没有信息量——它只能说明系统在金标集上没挂，
不能说明**是哪个模块让它不挂**。所以关掉某个模块再跑同一套用例，用差值衡量贡献。

复现命令：

```bash
python scripts/run_eval.py --ablate vector      # 关掉向量检索
python scripts/run_eval.py --ablate aliases     # 关掉 LLM 给出的英文别名
python scripts/run_eval.py --ablate repair      # 关掉 Cypher 自修复
python scripts/run_eval.py --ablate weak_prompt # 弱化提示词（去少样本 + 去数据规模提示）
```

## 结果

| 配置 | 用例 | 通过 | 通过率 | 相对完整系统 |
| --- | --- | --- | --- | --- |
| **完整系统** | 53 | 53 | **100.0%** | — |
| 去掉向量检索 | 53 | 43 | 81.1% | **−18.9pp** |
| 去掉英文别名链接 | 53 | 51 | 96.2% | −3.8pp |
| 去掉自修复闭环 | 53 | 53 | 100.0% | 0 |
| 弱提示词（仅 35 条图查询） | 35 | 35 | 100.0% | 0 |
| 弱提示词 + 关修复 | 35 | 35 | 100.0% | 0 |

### 1. 向量检索是语义分支的唯一来源（−18.9pp）

关掉后 10 条用例全部失败，且失败原因一致——「召回未命中」：

```
S01  有哪些清热解毒的中药？        期望召回「清热解毒药」
S02  补气的中药有哪些？            期望召回「补气药」
S03  活血化瘀的中药有哪些？        期望召回「活血祛瘀药」
S04  安神助眠的中药推荐一下        期望召回「安神药」
S05  利尿消肿的中药有哪些？        期望召回「利水渗湿药」
S06  补血的中药有哪些？            期望召回「补血药」
S07  化痰止咳的中药有哪些？        期望召回「化痰药」
S08  桂枝汤这类辛温解表的药有哪些？  期望召回「辛温解表药」
H05  最近总是睡不着，有什么中药能安神？
H10  补肾的中药有哪些？
```

这类问题没有可链接的实体（「手脚冰凉」「睡不着」不是图谱里的节点），
Text2Cypher 无从下手。这正是双路检索存在的理由——**不是「多一路更稳」，而是这一路覆盖了另一路的盲区**。

### 2. 英文别名链接决定跨语言查询能不能成立（−3.8pp）

失败 2 条，但失败方式很说明问题：

| ID | 问题 | 失败表现 |
| --- | --- | --- |
| A03 | 槲皮素一共作用于多少个靶点？ | 数值不符：期望 72 |
| H03 | 姜黄素作用于哪些靶点？ | F1=0.31，gold=5，**pred=27** |

A03 是「找不到」，H03 是更糟的一种——**找到了错的东西**：没有 `curcumin`
这个候选名，编辑距离模糊匹配把「姜黄素」匹配到了若干 curcumin 衍生物
（`bisdemethoxycurcumin` 等），于是返回 27 条看似合理但答非所问的结果。

这条比「返回 0 行」危险得多：0 行时模型会说「没找到」，而错误匹配会产出一篇
读起来很顺、结论错误的答案。**这也是为什么实体链接要做成「精确优先、模糊兜底」并且记录匹配方式**，
模糊匹配的结果在 prompt 里会被标注成「近似匹配」，让模型有依据地保守表达。

### 3. 自修复闭环：没有可测的收益，如实记录

触发率 1.9%（53 条里 1 条），关掉之后通过率**完全不变**。
把提示词也削弱（去掉少样本示例、去掉「TREATS 边密集必须 DISTINCT」的提示）后，
首次生成依然几乎全对，修复仍然没有可测收益。

结论要如实说：**在当前图谱 + 当前问法下，Schema 描述足够充分时，DeepSeek 首次生成的
Cypher 已经足够准，自修复基本不会触发，因此贡献不了可用数字。**

那为什么还留着它？

- 金标集是我按「系统该支持的问法」构造的，天然集中在图谱的能力范围内；
  真实用户会问图谱里没有的实体、新出现的成分名、拼写错误 —— 这些才是修复触发的场景；
- 修复的成本只在失败时产生，成功路径上零额外开销；
- 它把「失败」从「报错给用户」变成「再试一次」，是体验兜底而非指标优化。

**我没有为了让简历好看而虚构「60% → 90%」这类提升。** 如果被问到，
这个诚实的回答比一个编造的数字有价值得多——它说明我知道怎么测量，也知道测量结果不如预期时该怎么处理。

### 4. 指标口径说明（避免自我美化）

- 端到端通过率 **100%** 是在**我自建的 53 条金标集**上得到的。用例覆盖了系统设计的
  七类意图，天然偏向系统能力圈，**不能代表真实流量分布**。真实场景我估计会明显更低。
- `mode=set` 的用例：标准结果集 >30 时因系统受 LIMIT 约束只计算精度（返回的都对即通过），
  这会偏宽松；≤30 时算 F1。
- 忠实度 92.0%、切题度 0.71 是 LLM 评审，抽评 25 条，本身有噪声。
  忠实度唯一的误判是把答案里的「共 50 行」判成无依据，而该数字来自证据里的统计条目。
- 切题度偏低的主要原因是：回答会声明「仅展示前 10 条」，评审判为不完整；
  这是证据截断策略的副作用，不是事实错误。
